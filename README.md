# Auto-eject print loop for Bambu A1

Web app: upload an **STL**, choose **N** iterations, download a `.gcode.3mf`. The printer prints the part, cools the bed, pushes the part off with the gantry, and prints the next copy, N times.

The previous version (`previous implmentation/`) only post-processed `.gcode.3mf` files that had already been sliced. This rewrite slices in the app and checks whether a part can be ejected before it writes any G-code.

## How it is built

The app is generated by a [promptmap](https://github.com/conradbez/promptmap) DAG in `map/`. Each node does one job and has tests attached to it.

- **LLM:** OpenRouter `moonshotai/kimi-k3.1-pro`. The key is `OPENROUTER_API_KEY` in `.env`.
- **Review focus:** check the prompts and the final app (does it slice? does the eject G-code do the right thing?). Don't review the agent's intermediate code or reasoning.

## Key architecture decisions

| # | Decision | Why |
|---|----------|-----|
| 1 | **Slice in the app with the BambuStudio CLI** (Docker), using the stock A1 profile | The output is a native `.gcode.3mf` that the printer accepts. |
| 2 | **Inject the eject block as the slicer's `machine_end_gcode`**, not by pasting text into finished G-code | The Factorian end block uses slicer placeholders (`{max_layer_z}`, `{if …}`). The old app pasted them in unevaluated, which produced broken G-code. Passing the block to the slicer gets the placeholders filled in. |
| 3 | **Loop = repeat the full start→print→end block N times** | This is the proven Factorian Designs method, and it needs no firmware changes. |
| 4 | **Ejectability check is deterministic Python (`trimesh`)**, not an LLM | It is geometry, so the same STL always gets the same verdict, and it can be tested. |
| 5 | **FastAPI + one static page with three.js**, replacing hstream | The 3D preview and the simulation need client-side JS. |
| 6 | **Fallback: accept a `.gcode.3mf` that is already sliced** (the old path) | Gives a working route if the slicer CLI fails in the container (the biggest risk). |

## Scope

| Item | Decision | Difficulty | Reason |
|------|----------|------------|--------|
| STL → G-code slicing | ✅ Include | Medium-hard | The core feature. Risk: running the slicer CLI headless in Docker. |
| Repeat bed heat/cool cycle to loosen the print | ✅ Include, configurable | Easy | Already in the end block. Expose the temperatures, hold times and cycle count in the UI. |
| Check whether the print can be flicked off | ✅ Include | Medium | Uses height (the gantry push needs about 32 mm or more, otherwise the nozzle pushes), base contact area, tip-over ratio (height ÷ base) and footprint position. Returns pass / warn / fail with a reason. |
| Research into existing solutions | ✅ Include (one map node) | Easy | A short comparison: Factorian, plate-swap systems, print-farm tools. LLM output, so every link has to be checked. |
| G-code motion simulation | ⚠️ Include, minimal | Medium | Bounding boxes for the toolhead, gantry and bed, plus a box for the STL. Replays the end block and flags collisions or a missed push. Uses `gcode-preview` (three.js) to view the print. |
| Full CAD model of the A1 for assessment or simulation | ❌ Exclude | Hard | Boxes are enough for collision and push checks. A detailed model adds cost and the checks get no more accurate. |
| External motor / mechanism to flick prints off | ❌ Exclude (note only) | Hard | Needs hardware, wiring and firmware sync. Gantry push-off already works. |
| Printable CAD riser to raise the A1 | ❌ Exclude (link only) | Easy, low value | Community risers already exist. Link to them in the usage docs. |
| A1 mini (and other printers) | ❌ Exclude | Easy later | v1 targets the A1 only: one end block, one bed size, one real fixture. |
| Printer connectivity (send over LAN / cloud) | ❌ Exclude | Medium | Download and print from SD or Bambu Studio for now. |
| OrcaSlicer fork | ❌ Exclude | Very hard | Means maintaining a fork of a large C++ codebase and rebasing every release, for little gain over the CLI. |
| OrcaSlicer plugin | ⏸️ Defer to v2 | Medium | The Python plugin API only exists in the 2.5.0 Alpha (Oct 2026) and may change before stable. It can't create or edit presets. v1 keeps the ejectability check and end-block generation in a plain Python package (`autoeject/`), so a plugin can later be a thin wrapper around it. |

## Risks

- **BambuStudio CLI in Linux Docker** may need extra libraries or a virtual display. If so, use the pre-sliced fallback (decision 6).
- **Eject failures can damage the printer** (the part jams, the head crashes). The UI blocks parts that fail the check and shows warnings before download.
- **Pre-sliced files** carry Bambu's evaluated stock end block between `; MACHINE_END_GCODE_START` and `; EXECUTABLE_BLOCK_END`. The app swaps exactly that span for the eject block, fills its placeholders from the file header (e.g. `max_z_height`), and recomputes `plate_1.gcode.md5`.
