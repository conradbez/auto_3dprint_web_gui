> This page describes the architecture of OrcaSlicer's Python plugin system. Python plugins run inside an embedded CPython interpreter, so users can extend OrcaSlicer without recompiling the application or patching the C++ core.
>
> Capabilities, not single-purpose plugins - one plugin is a package that registers one or more capabilities, each a typed unit of functionality (e.g. post-processing, script, printer-connection). Each capability type has a fixed C++ entry point and is invoked at a specific place in the app; a plugin's "types" are simply the set of capability types it registers.
>
> A permission boundary, not a sandbox - filesystem, network, process-spawn, and thread-creation operations by plugin code are categorized and gated by an audit hook that prompts the user and remembers the answer per plugin; a plugin can also declare what it expects up front with orca.request_permissions(...).
>
> The entry file is either a single .py file (metadata in a PEP 723 comment block) or a .whl wheel (metadata from the wheel's METADATA). The capabilities the plugin registers determine which workflows can run it; there is no separate type declaration in the metadata.
>
> 4. PluginLoader::load_plugin() (worker thread, serialized)
> │ ├─ install dependencies via bundled `uv`; extract bundled .whl deps onto sys.path
> │ ├─ begin capture → import module (runs @orca.plugin, marking the package class)
> │ ├─ finalize capture → instantiate package, call register_capabilities(),
> │ │ collect its request_permissions() declarations
> │ ├─ if permissions were declared, show one combined dialog;
> │ │ a No aborts the load before any capability is created
> │ ├─ instantiate each registered capability and cache its get_name()
> │ ├─ set_audit_plugin_key(descriptor.plugin_key) // audit identity
> │ ├─ on_load() (under the GIL)
> │ └─ store the capabilities; fire on-load + on-capability-load callbacks
>
> Security - all C++ to Python calls cross a trampoline that opens a per-call audit context; the PluginAuditManager audit hook then categorizes sensitive filesystem, network, process-spawn, and thread-creation events, prompts the user with a Yes/No dialog naming the target, and persists most categories' grants per plugin. A plugin can declare the targets it expects with orca.request_permissions(...), which produces one combined prompt during load.

> Each plugin lives in its own subdirectory containing exactly one entry file: either a single .py file or a single .whl (wheel).
>
> OrcaSlicer reads identity and dependency metadata from a PEP 723 inline script metadata block: a comment block delimited by `# /// script` and `# ///`, with each content line prefixed by `#`. Identity fields live in a `[tool.orcaslicer.plugin]` table; dependency fields live at the TOML root. Parsing is implemented in PythonFileUtils.cpp::parse_pep723_toml / read_python_plugin_metadata.
>
> # /// script
> # requires-python = ">=3.12"
> # dependencies = []
> #
> # [tool.orcaslicer.plugin]
> # name = "Sample Plugin"
> # description = "Appends a short build-environment note to the exported G-code."
> # author = "Your Name"
> # version = "1.0.0"
> # ///
>
> Field | Location | Required | Notes
> name | [tool.orcaslicer.plugin] | recommended | display name in the Plugins dialog
> description | [tool.orcaslicer.plugin] | recommended | shown in the plugin Description tab
> author | [tool.orcaslicer.plugin] | optional |
> version | [tool.orcaslicer.plugin] | recommended |
> dependencies | TOML root | optional | array of pip requirements (see Dependencies)
> requires-python | TOML root | optional | read but not stored or enforced against the bundled interpreter today

> Note
> The metadata block no longer declares a type. A plugin's type(s) are derived from the capability classes it registers (each capability's get_type()), so the same metadata block is used whether the plugin offers one capability or several. The PEP 723 parser (parse_pep723_toml) reads only name, description, author, version, requires-python, and dependencies; any other key (including a stray type = ...) is ignored. The same applies to .whl plugins: identity comes from the wheel's METADATA, and the served types come from the registered capabilities.

> Capability configuration
> Every capability has a JSON configuration, regardless of its capability type. The Config tab in the Plugins dialog uses the host's JSON editor unless the capability supplies a custom HTML UI. The global configuration is stored under data_dir()/orca_plugins/config.json and is keyed by the full capability identity (plugin key, capability type, and capability name).
>
> The configuration methods are available on orca.PythonPluginBase:
> has_config_ui() -> bool | Return True to use the custom UI returned by get_config_ui() instead of the JSON editor.
> get_config_ui() -> str | Return a self-contained HTML string. An empty or failing result falls back to the JSON editor.
> get_default_config() -> str | Override the method to return a Python dict; OrcaSlicer exposes the resulting JSON as a string and uses it when the user restores global defaults. Without an override, the default is {}.
> get_config() -> str | Return this capability's effective stored configuration as a JSON string. It is {} when no configuration has been saved.
> get_config_version() -> str | Return the plugin version that last saved the configuration. Use this to detect and migrate an older schema.
> save_config(config: str) -> bool | Persist a JSON string for this capability. Use json.dumps(config_dict) and check the return value.
>
> Base class | get_type() returns | Required methods | Invoked by
> orca.script.ScriptPluginCapabilityBase | Script | get_name(), execute(self) -> ExecutionResult | the Plugins dialog -> Run action
> orca.pages.PagesPluginCapabilityBase | Pages | get_name(), get_ui(self) -> str | a main-window tab added while the capability is enabled
> orca.slicing.SlicingPipelineCapabilityBase | SlicingPipeline | get_name(), execute(self, ctx) -> ExecutionResult | configured slicing steps and G-code export / post-processing
> orca.printer_agent.PrinterAgentBase | PrinterConnection | get_name() + ~30 agent methods (get_agent_info, connect_printer, ...) | the network / printer-agent layer on load; ... the printer preset's printer_agent field selects the agent ID
> orca.resource_texture.ResourceTexturePluginCapabilityBase | ResourceTexture | get_name(), get_texture_dir(self) -> str | OrcaSlicer, when the capability is materialized

> The slicing context (orca.slicing.SlicingPipelineContext) is passed to execute and exposes the live slicing graph during geometry steps. At Step.psGCodePostProcess, the graph fields are None and the context instead exposes the working G-code file:
> orca_version | OrcaSlicer version string (inherited from PluginContext)
> step | the pipeline step currently being executed
> print | the live print graph, or None at psGCodePostProcess
> object | the current print object for object-scoped steps, or None
> gcode_path | the working G-code path, set at psGCodePostProcess
> host | target host, when exporting to a network printer
> output_name | the output file name
> config_value(key) | the resolved print configuration value, or None if absent
> cancelled() | whether the active print has been cancelled
>
> Important
> Filesystem, network, process, and thread-creation access are audited. While execute() runs, a sensitive operation (a file read/write/create/delete, an HTTP/socket connection, spawning a process, or starting a thread) prompts the user with a Yes/No dialog naming the target; a "Yes" is remembered for that plugin so the same target does not prompt again. Thread creation is granted once per plugin: the work the spawned thread then runs is not audited. An operation inside a pre-determined allowed folder — data_dir(), the read-only resources_dir(), or (at psGCodePostProcess) the current G-code file's folder — needs no prompt at all; a secrets/ cert/ conf-like path is blocked outright, with no prompt either. To avoid first-use prompts, declare what you need with orca.request_permissions(...) in register_capabilities().

> Multi-capability plugin: one package that exposes a slicing-pipeline capability and a script capability.
>
> # /// script
> # [tool.orcaslicer.plugin]
> # name = "Sample Plugin"
> # description = "Demonstrates registering several capabilities from one plugin."
> # author = "Your Name"
> # version = "1.0.0"

> class EnvironmentReport(orca.slicing.SlicingPipelineCapabilityBase):
>     def get_name(self):
>         return "Environment Report"

>     def execute(self, ctx):
>         # Post-process the exported file at the dedicated pipeline seam.
>         if ctx.step != orca.slicing.Step.psGCodePostProcess:
>             return orca.ExecutionResult.success()
>         try:
>             with open(ctx.gcode_path, "a", encoding="utf-8") as f:
>                 f.write(f"\n; processed by Environment Report for {ctx.output_name}\n")
>         except Exception as exc:
>             return orca.ExecutionResult.failure(
>                 orca.PluginResult.RecoverableError,
>                 f"could not append report: {exc}")
>         return orca.ExecutionResult.success("report appended")
>
> class GCodeBenchmark(orca.script.ScriptPluginCapabilityBase):
>     def get_name(self):
>         return "G-code Benchmark"
>
>     def execute(self):
>         return orca.ExecutionResult.success("benchmark complete")
>
> @orca.plugin
> class SamplePlugin(orca.base):
>     def register_capabilities(self):
>         orca.register_capability(EnvironmentReport)

> List third-party requirements in the PEP 723 root dependencies array. On install, OrcaSlicer resolves them with a bundled uv into the plugin's environment (PluginLoader.cpp):
> # dependencies = ["requests==2.32.3", "humanize"]

> The embedded plugin API is exposed through a single Python module named orca (PYBIND11_EMBEDDED_MODULE(orca, ...) in PythonPluginBridge.cpp).
>
> Execution Results
> ExecutionResult is how a plugin reports the outcome of a run:
> orca.ExecutionResult.success(message="", data="")
> orca.ExecutionResult.skipped(message="")
> orca.ExecutionResult.failure(status, message, data="")  # status is an orca.PluginResult
> status - an orca.PluginResult. message - human-readable text; this is what surfaces in error/result dialogs. data - a free-form string whose meaning is defined by the plugin/workflow (not interpreted by the framework).
>
> Registration
> Capabilities - each capability is a class that subclasses a typed base and implements get_name(self) -> str. The name is how the capability appears in the UI and how presets refer to it, so it must be unique within the plugin and must not contain a ;. That character is reserved as a separator in preset references, and a ; in a capability name fails the load.
> The package - exactly one class per file is decorated with @orca.plugin and subclasses orca.base. Its register_capabilities(self) method calls orca.register_capability(Cls) once for each capability class you want to expose:
>
> @orca.plugin
> class SamplePlugin(orca.base):
>     def register_capabilities(self):
>         orca.register_capability(GCodeBenchmark)
>         orca.register_capability(EnvironmentReport)
>
> OrcaSlicer instantiates the package class (it must be callable as SamplePlugin() with no arguments), calls register_capabilities(), then instantiates each registered capability.
>
> Rules enforced when a plugin loads (most in PythonPluginBridge.cpp):
> The @orca.plugin class must subclass orca.base, and there must be exactly one per file. A second @orca.plugin fails the load.
> Each class passed to orca.register_capability must subclass a capability base (ultimately orca.PythonPluginBase); otherwise it raises value_error.
> Every capability must resolve get_name() (checked in the bridge); the loader (PluginLoader.cpp) additionally rejects the plugin if the resulting (type, name) pair is not unique across it.
> A capability class you never pass to register_capability is invisible to OrcaSlicer, even if it is defined in the file.
> If the plugin calls orca.request_permissions(...), the user must accept the combined dialog that follows registration; declining it fails the load.
>
> Permissions
> orca.request_permissions(...) declares, from register_capabilities(), the filesystem, network, process, and thread access the plugin expects. All parameters are optional:
> orca.request_permissions(
>   fs_read=[],          # filesystem paths to read
>   fs_readwrite=[],     # filesystem paths to read/write
>   network_http=[],     # URLs
>   network_socket=[],   # socket addresses, as str() renders them
>   process=[],          # commands / argv
>   threading=False)     # True requests the fixed "thread" target
> Each list takes the target strings the corresponding audit event reports: paths for the filesystem buckets, a URL for network_http, an address string such as "('example.com', 443)" for network_socket, and a command for process.
> threading=True requests permission to create one thread; thread creation is granted once per plugin, and the new thread's own work is not audited.
> OrcaSlicer collects the declarations while register_capabilities() runs and shows one combined Yes/No dialog after it returns and before any capability instance is created. Targets already granted to the plugin are skipped, so declaring them again does not prompt.
> Declining the dialog aborts the plugin load. An empty string in any list, or calling the function outside plugin discovery, raises ValueError.
>
> Capability Names and Types
> get_name() is required; get_type() usually is not. Every capability must implement get_name(). It is pure virtual on the root base, and a missing override fails the load. The typed C++ bases already implement get_type() (for example, ScriptPluginCapability::get_type() returns Script), so a subclass of a typed base does not need to override it.
>
> Every capability inherits the optional hooks on_load(), on_unload() and on_lifecycle_event(event, ctx) (see Lifecycle Events) from orca.PythonPluginBase, along with these configuration methods: has_config_ui(), get_config_ui(), get_default_config(), get_config(), get_config_version(), save_config(config).

> This page describes the CPython audit hook used by OrcaSlicer's plugin system. Python can read and write files, spawn processes, open sockets, and load native code, so plugin actions in these categories prompt the user for a Yes/No decision before CPython performs the operation, and remembered answers are persisted per plugin.
> Note This is an interactive permission system, not a sandbox: a user who clicks Yes has authorized the action, and there is no isolation layer stopping a genuinely malicious plugin from doing damage after that. Today it categorizes and gates filesystem, network, process-spawn, and thread-creation events; native-code loading (ctypes) is not audited, and what a plugin-spawned thread does after it starts is not attributed to the plugin.
>
> enum class AuditEventCategory {
>   None, FsRead, FsReadWrite, FsCreate, FsDelete, Http, Socket, ProcessCreate, Threading,
> };
>
> 4. The Decision Pipeline
> audit_hook resolves the category first (None -> allow, unaudited), then walks through:
> Denied-path check (fs categories only — is_denied_path ...). If any target is a denied filename or matches a denied path keyword, block immediately: report_denied, no dialog ...
> Ancestor-cascade check. If the current Python call stack already contains a stdlib frame approved for an earlier event in the same call chain, allow immediately with no dialog.
> Allowed-root shortcut (fs categories only — check_path_access). If every target resolves inside an allowed root — and, for a write/create/delete-shaped event, a root that permits writes — allow immediately with no dialog and nothing persisted.
> The rest funnels through PluginAuditDetail::decide_audited_event: ... Show one dialog for everything still unresolved (audit_message + a Yes/No message box). On Yes: persist each newly-approved target ... On No: report_denied records an AuditViolation, raises PermissionError in the calling interpreter, and the hook returns -1 ...
> The dialog is modal and its answer applies to the current event when the event fires on the main/UI thread. An event can also fire on a thread the UI thread may itself be waiting on (the slicing-pipeline hook runs on the slicing worker). Blocking that thread on a dialog would deadlock the application, so the prompt is posted to the UI thread asynchronously, the current event is denied (fail closed, exactly like an unanswered prompt), and a Yes is persisted when the user accepts. The plugin's next attempt at the same target therefore succeeds without a prompt.
>
> Persistence
> Persisted categories map onto PluginPermissions (PluginFsUtils.hpp) 1:1:
> FsRead -> fs_read
> FsReadWrite -> fs_readwrite
> Http -> network_http
> Socket -> network_socket
> ProcessCreate -> process
> Threading -> threading (always the fixed target thread)
> FsCreate, FsDelete (none — never persisted)
>
> Allowed Roots and Denied Paths
> install_hook() populates both roots and both deny registries:
> Root | Access | Covers
> data_dir() (global) | read+write | each plugin's storage folder (data_dir()/orca_plugins), the installed/system profile cache (data_dir()/system), and the rest of data_dir()
> resources_dir() (global) | read-only | the app's bundled, shared assets ...
> current G-code file's parent directory (scoped, SlicingPipelinePluginCapabilityTrampoline::execute()) | read+write | only while a psGCodePostProcess call is on the stack, and only for that call
> Denied filenames: default_denied_filenames() ... Denied keywords: default_denied_path_keywords() = {"secret", "cert", "conf"} ...
>
> A declaration pre-approves only the exact target strings listed; any other access still prompts on first use.
> Granted permissions belong to the installed package, not just the plugin key: every successful install ... clears the permissions block of that plugin's sidecar (PluginManager::revoke_plugin_permissions()), so the new code must be granted access again.

> Any capability can observe application lifecycle moments (project open/save, slicing, plate and object edits, preset changes, printer and job activity) by overriding on_lifecycle_event(). >     if event == orca.LifecycleEvent.ProjectAfterSave:
>         print("saved", ctx.name)
>     elif event == orca.LifecycleEvent.SlicingJobComplete and ctx.code == orca.LifecycleEvtCode.Error:

> 🧩 Plugins
> OrcaSlicer 2.5.0 introduces Python plugins, a supported way to add your own features to the slicer without maintaining a fork. A plugin can add one-click scripts, step into slicing to reshape layers or rewrite the G-code, add its own tab or docked panel, or react to events like a finished print. Open Plugins from the main menu to install a plugin from a file on your computer or from Orca Cloud; a plugin must ask your permission before it reaches outside OrcaSlicer's data folder, goes online or starts other programs. The plugin system is new and its API may still change, so feedback from users and plugin authors is very welcome. Getting started with plugins · Plugin development guide
>
> OrcaSlicer now runs plugins written in Python on a Python runtime that ships with the app, so there's nothing extra to install. A plugin is either a single .py file or a .whl package, and any Python packages it depends on are installed for it automatically (on Windows ARM64 too). ... One plugin can provide several features, called capabilities. Script actions run when you click Run in the Plugins window or pick them in the Speed Dial. Slicing Pipeline steps run while you slice. Pages add their own tab to the main window. Resource Texture packs add their own height-map textures to the Texture Displacement picker.
>
> Slicing-pipeline plugins by @SoftFever in 14721
> A plugin can now take part in slicing itself. Pick one or more under Process > Others > Slicing Pipeline Plugin (Advanced mode), and they run at set points while the model is sliced. There, a plugin can read and edit the sliced layers, and the walls, infill, preview and final G-code all follow its changes. It can also edit the exported G-code file as a final post-processing step. Plugin errors show up as ordinary slicing errors rather than crashing OrcaSlicer. The PR includes sample plugins: one twists, tapers or wobbles any model as it slices, and one applies fuzzy skin to the sliced outline itself, so the infill follows the fuzzy wall too. This is experimental and aimed at plugin developers and testers.

> Permission prompts for plugins by @SoftFever, @peachismomo and @HanifKoh in 14821, 14989, 16243, 16248, 16254, 16255 and 16253
> Plugins can't read OrcaSlicer's own config file or your Orca Cloud login token, which hold account and printer access details. Folders named like secrets, certs or config, and .conf/.ini files, are blocked the same way. When a plugin tries to work with files outside OrcaSlicer's data folder, connect to the network, launch another program (or replace OrcaSlicer with one) or start a background thread, a prompt names the plugin and what it wants. OrcaSlicer remembers your answer for that plugin. A plugin can also list the files it needs up front, so you're asked once when it loads. ... This is a permission system, not a sandbox, so only install plugins from sources you trust.

Looked in: same wiki plugin pages plus Brave searches "OrcaSlicer plugin repeat print N times", "OrcaSlicer plugin end G-code Bambu Lab A1".
